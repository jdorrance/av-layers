# Serving resource budgets

These are the candidate's admission limits and a memory estimate declared before external qualification. They are not a guarantee about V8's exact heap layout. Production admits only GFS. Synthetic products exercise the same serving path through a separate local Worker entrypoint.

## Cache and in-flight limits

- Pointer cache: 32 entries and 1 MiB accounted decoded bytes; positive TTL 15 s, unavailable-publication TTL 5 s. A membership miss queues/coalesces a real pointer refresh, waiting at most the remaining one-second throttle window. A cached miss is never treated as definitive solely to save a refresh.
- Manifest cache: 64 entries and 4 MiB accounted decoded bytes, bounded by build expiry; four simultaneous distinct cold manifest loads. Pointer and manifest JSON accounting estimates strings, keys, values, array slots and object overhead instead of multiplying serialized bytes.
- Coverage cache: 16 entries and 8 MiB accounted bitsets, layout indexes and descriptor overhead; two distinct concurrent loads. Descriptor identity and each bitset digest are verified before admission; publication geometry is rechecked on cache hits.
- PMTiles directory cache: 256 entries and 4 MiB accounted storage, using 96 bytes per decoded directory entry. Four distinct tile operations can be in flight. Directory entry count is capped at 16,384 before the library creates entry objects.
- Binary sample/provenance reads: eight concurrent distinct loads; identical reads share materialized bytes. No R2 body or Response stream is shared between requests.
- All streaming object reads/decompression and active provenance verification share a 32 MiB allocation pool. Reads use one preallocated buffer plus its bounded result; provenance verification holds a 12 MiB reservation through hash and schema checks. Outgoing responses have a separate 16 MiB pool, reserving four times body size for payload, serialization and cache/response copies before body construction, held until both client and Cache API branches consume, cancel or reach their deadline. JSON serialization also reserves from the shared allocation pool before allocating its string. HEAD/304 paths cancel discarded bodies. Each coalescing group admits at most 32 owners/joiners across all its keys. The pointer membership-refresh delay creates one shared timer per operation. Distinct cold operations and body reads time out after 15 s and abort pending stream consumption. An admission failure returns uncached 503; it does not enqueue an unbounded backlog.

Object limits: pointer 128 KiB, manifest 512 KiB, coverage descriptor 32 KiB, each coverage bitset 512 KiB, provenance 1 MiB, compressed or decompressed archive range 1 MiB, sample range 256 KiB. Before parsing, metadata JSON permits 8,192 structural tokens; provenance permits 65,536 to admit the current GFS receipt (55,760 observed). Both cap nesting at 32 and each object/array at 256 entries. The current real receipt is 725,946 bytes, at most 26 object keys and 53 array entries; these fixtures must remain admitted. The request URL cap is 16 KiB. Selection limits come from immutable descriptors, bounded by the shared contract ceiling.

## Memory qualification model

For the supported GFS workload and the qualification cap of 20 concurrent requests, reserve 17 MiB for all admitted caches, 32 MiB for simultaneous stream buffers, and 24 MiB for outgoing response permits (16 MiB) and transient parsed metadata/coverage/directory overhead (8 MiB). Provenance verification is already reserved inside the shared 32 MiB pool. Reserve a further 22 MiB for the Worker runtime, stacks and unmodeled allocation overhead. Total modeled envelope: **95 MiB**, below the 96 MiB local surrogate gate and the 128 MiB platform limit. Decoded object estimates are assumptions; the profile must validate them. Cache capacity is a ceiling, not a promise that every archive remains resident. Arbitrary adversarial payloads must hit admission limits; the measured supported-workload envelope is not a universal heap bound.

`pnpm exec node --import tsx scripts/profile-worker-memory.ts --inspector http://127.0.0.1:9229 --duration-seconds 310 --output /tmp/worker-memory.json` samples `Runtime.getHeapUsage` every 100 ms without forced GC. Run it concurrently with local load. The report includes allocated JavaScript heap, backing storage and embedder heap where available. It is a sampled **local workerd surrogate**, not deployed-isolate peak memory. Any unavailable metric must remain disclosed.

## Runtime and external load checks

`pnpm exec node --import tsx scripts/test-worker-runtime.ts` uses disposable local R2 and a real workerd listener. Eight overlapping requests must share one R2 read and still complete when the initiating client disconnects. It never accesses a remote bucket.

`pnpm exec node --import tsx scripts/benchmark-api.ts --base-url URL --lat LAT --lon LON` records a short first-observed/warm/conditional/outside/unknown-build run. First observed does not imply a fresh isolate. The per-request `X-Av-R2-Reads`, `X-Av-R2-Bytes`, `X-Av-Cache-Hits`, `X-Av-Coalesced` and `X-Av-Response-Cache` headers expose actual serving work. `Server-Timing: worker` is elapsed time including I/O, not CPU. Enable `AV_REQUEST_METRICS=true` for aggregate structured request logs; logs omit point coordinates and use coarse route categories.

For response-cache qualification, deploy the same staging candidate with `AV_RESPONSE_CACHE=off`, run `--load --mode uncached --duration-seconds 300 --location REGION`, restore the normal on configuration, and run `--load --mode warm --duration-seconds 300 --location REGION`. The option is a deployment binding; clients cannot bypass cache via query strings or request headers. The script paces 10 requests/s, 90% tile / 4% sample / 6% metadata, at most 20 concurrent requests. A full run contains 3,000 requests including 120 samples; each route must meet its minimum observation count. There are only two sample warmups; do not run another sample benchmark in the preceding minute against the same source IP. Record code revision and each deployment configuration separately. Final qualification uses normal response caching.

Reports measure full response-body latency and report response-cache evidence, failures, dropped scheduling slots and p50/p95. CPU requires platform telemetry. Deployed GFS, sustained-load, real Windy-host and release checks remain separate gates; local synthetic results cannot satisfy them.
